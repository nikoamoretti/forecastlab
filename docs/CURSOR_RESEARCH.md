# Cursor research

Research for the daily forecasts is done by `cursor-agent` on the owner's Mac, on his Cursor plan, with a non-Claude model. Claude never searches the web for a forecast: it reads a digest of the evidence and forecasts. This keeps Claude's token use small and the researcher separate from the forecaster and the judges.

## The daily flow (weekdays, Pacific time)

1. A LaunchAgent (`ai.forecastlab.research`) runs `scripts/mac_research.sh` every 30 minutes. The script updates its clone to `grok/forecastlab-mvp` and runs `scripts/cursor_research.py daily`, which does nothing unless it is a weekday inside the `window_hours` of `configs/research.json`, read in its `window_tz`, and today's research has not been pushed. The window is in Pacific time (02:00-08:00), so it moves with US daylight saving time: 09:00-15:00 UTC in summer, 10:00-16:00 UTC in winter. The older `window_utc` key still works and is read in UTC.
2. It creates `claude/daily-forecasts-<date>` (with a `-dryrun` suffix while `mode` is `dry_run`) and asks the **Daily run steps** workflow to `prepare` the questions, then waits for it.
3. It runs `cursor-agent -p --trust --force --mode ask --model <model>` in an empty temporary folder for every new question, `parallel` questions at a time, in **three passes** (`passes` in `configs/research.json`), each one agent run, in order (`forecastlab.cursor_research`):
   - **Pass 1, the outside view:** the reference class of comparable past cases (earlier releases of the same statistic, votes, launches, rulings) with counts and the period, counted from primary data where possible. It yields `base_rate`, facts and sources.
   - **Pass 2, the inside view:** told pass 1's base rate, facts and pages so it does not repeat them, it looks for the latest facts from primary sources (central banks, statistics offices, election boards, courts, filings, schedules) and the last 7 days of reporting: what is different this time (`different_now`), the events scheduled before resolution, and the unknowns. It also works through the question's topic checklist from `configs/research_checklists.json` (see below).
   - **Pass 3, the other side:** told what passes 1 and 2 found, it picks the outcome that evidence makes less likely and looks for the strongest evidence for it (`against`), plus any weaknesses in the evidence so far (a stale number, a secondary source, a definition that differs from the rule). It gives no probability or lean either.

   Every pass carries the same rules: no forecast, primary sources first, only information published before now, never prediction markets, betting or odds, quotes copied word for word from opened pages. The three replies are checked one by one (`validate`: valid JSON, no market site, no sentence naming a market or odds; pass 1 needs at least 2 sources and 2 facts, passes 2 and 3 at least 1 of each, and pass 3 needs an `against` text) and merged (`merge`) into the one findings shape `research.json` has always had: sources de-duplicated by URL (a repeated page keeps the quotes of both passes, up to 5) and at most 14 in all, with every fact's source index remapped; facts concatenated in pass order with repeats dropped; `base_rate` from pass 1, `different_now` from pass 2, `uncertainties` pooled, and the new `against`. Each question's findings also list `passes_done` (for example `["outside", "inside", "against"]`) and, if a later pass failed or was skipped, `passes_failed` with the reason. If pass 1 fails the question counts as failed, as before and nothing more is sent for it; if pass 2 or 3 fails, the passes that worked are kept. `passes` can be 1 (one combined run asking for all of it, the Claude fallback's setting), 2 (no pass 3) or 3.
4. Failed questions are logged under `failed` and skipped; they do not stop the run. Questions run `parallel` at a time; the passes of one question run one after the other.
5. It saves `research.json` and pushes it with a `download` request. The workflow runs `scripts/research_download.py`, which downloads each cited page (HTML or PDF), keeps the text around the quotes, and marks each source `verified` (every quote found), `false` (page read, quote missing) or `null` (page not downloadable).
6. The routine reads the evidence with `python scripts/cursor_research.py digest <dir>`, forecasts, writes briefs, and asks for `finish`. Judges read the same excerpts. The digest lists the facts, the base rate, "Different this time", then "Case for the other outcome" (pass 3), the unknowns and the sources. `build_track_record.py` also copies `against` and `passes_done` into `data/research/<dir>.json`.

## Limits and failure

- **Cost:** none beyond the Cursor plan. Each run uses about 100,000 tokens on Cursor's side and shows as Included; three passes make a question cost about three times what it did. The CLI cannot read the plan's usage meter, so the job keeps its own count in `~/.forecastlab/ledger.json` and stops at `daily_run_cap` runs a day and `weekly_run_cap` a week. Both count agent runs, one per pass, and only runs actually made (a question skipped after a usage limit costs nothing). A question is started only if all its passes fit in what is left, and questions are researched in file order, so a capped day researches the first ones. Thirty questions take 90 runs against the daily cap of 120 (room for 40 questions); five such days are 450 of the weekly 1,000.
- **Usage limit reached:** the first error that says a usage, rate or quota limit was hit, in any pass, stops the run from sending anything more: the question it hit keeps the passes that finished (the rest are listed under `passes_failed` as skipped) and the remaining questions are marked skipped, because the weekly limit fails every call until it resets. The routine's `fill` step then researches the questions with no research with Claude.
- **Pages that refuse the checker:** many sites refuse requests from GitHub's machines. `research_download.py` asks a refused page again as a browser would, then reads its latest Internet Archive copy (marked `checked_via: "archive"`); a copy older than the source's publication date leaves it unchecked. Re-checking Oct 19-23 with this (261 sources) cut the unchecked share from 30% to 25% and raised fully confirmed sources from 116 to 122. The rest are mostly sites the archive has not saved and pages whose text only appears with JavaScript.
- **What each question took:** `research.json` keeps the seconds each run took under `seconds` and, for Claude runs, the reported cost under `cost_usd`. Both show on the question's page.
- **Mac asleep or job failed:** the LaunchAgent catches up when the Mac wakes. If `research.json` has not landed by 15:00 UTC, the routine skips the day: no forecasts, no judge spend.
- **Claude fills the gaps (owner's call, 2026-10-23):** when Cursor fails for a question (its weekly limit, a timeout) or the Mac job never ran, the daily routine runs `scripts/cursor_research.py fill`. It sends a single combined prompt (outside view, inside view with the topic checklist, the other side, in one run: `fallback.passes` is 1, to save Claude tokens) to a headless `claude -p` run (`fallback` in `configs/research.json`: Sonnet, low effort, only the WebSearch and WebFetch tools, in an empty folder) for every question still without research, checks the answers the same way, records the model in `researched_by`, and pushes with a `download` request. The prompt asks every researcher for official sources first and for quotes copied from the page text it opened, never from a search snippet; Claude runs in the cloud often cannot open pages, so their quotes check worse (33% of readable pages passed on Oct 23, against 74% for Cursor). The forecaster is a different run that only reads the digest, and the Claude judge sits out the questions Claude researched.
- **Independence:** `model_family` (and `fallback.model_family`) in `configs/research.json` name the researchers' families. `judge_panel.py` refuses to run when a judge's model id contains `model_family`; a judge from `fallback.model_family` (Claude) skips each question whose `researched_by` names its family. The research model is never a forecaster. Change the model and the family together.
- **Dry run:** while `mode` is `dry_run` the branch is `claude/daily-forecasts-<date>-dryrun`, the routine forecasts nothing from it, and no judge money is spent. Set `mode` to `live` to go live. The three passes and the topic checklists were approved by the owner on 2026-10-31. The first three dry-run days (Oct 14 to 16, 2026) researched every question with no failures; 45 to 63 percent of the cited sources had every quote found on the downloaded page, and the rest were either unreachable from Actions or did not contain the quoted sentence. `mode` is `live` from 2026-10-17.

## Setup on the Mac

The job needs `cursor-agent` signed in, `git` with push access to `nikoamoretti/forecastlab`, and Python 3.9+ (`python3`) on the LaunchAgent's `PATH`. The job uses its own clone at `~/.forecastlab/repo` (set `FORECASTLAB_REPO` to change it) and a scratch worktree at `~/.forecastlab/work`.

Hand test of three questions, nothing pushed: `scripts/mac_research.sh --dry-run --branch claude/daily-forecasts-<date>-dryrun`.

## Topic checklists

`configs/research_checklists.json` holds, per topic as it appears in the questions (Interest rates, Economy, Politics, Crypto, Jobs, ...), at most 6 concrete research instructions: `{"version": 1, "topics": {"Interest rates": ["...", ...]}}`. Pass 2 (and the Claude fallback's combined pass) lists the items for the question's topic and asks the researcher to record what it finds for each as a dated, sourced fact, or to say under uncertainties that it could not. A topic with no entry gets no checklist; the cohort questions take their topic from their series (`treasury_10y` is Interest rates, the claims, payrolls and unemployment series are Jobs, `cpi` is Inflation). The file is seeded from the forecaster's own resolved misses (Oct 2026): the 10-year yield thresholds that were all called "above" while yields fell (take the level from the official series, count the days and the typical move, list the scheduled releases), the central-bank and statistics-office calls missed on stale or unopened evidence, the narrow range questions, the price-touch questions and the election calls that discounted polls. Items never mention markets or odds; `load_checklists` and `miss_review.py apply` refuse them.

## Learning from misses

The researcher gets better only if what the misses teach reaches its instructions. `scripts/miss_review.py` closes that loop with two commands (run them about weekly, or when five or more new misses have resolved; nothing schedules them yet):

1. `python scripts/miss_review.py export [--since YYYY-MM-DD] [--out packet.json]` prints a JSON packet of Claude's misses from `data/track_record.json`: every wrong call and every resolved forecast with a squared error of 0.36 or more. Per miss: id, date, topic, question, resolution rule, Claude's probability and rationale, the outcome, and the research it had (base rate, what was different, facts, unknowns, the passes that ran: `legacy_single` for research from before the three passes, and how many sources had every quote found). It also lists the allowed causes and the current checklists. By default it covers misses on or after the newest `data/miss_reviews/*.json` that no review lists yet (everything, if there is no review); `--since` lists every miss from a date on. The packet holds no market price: the rules and rationales pass the same market filter as the research, and market snapshots are never read.
2. The reviewer (a Claude session reading the packet) writes a review file, one entry per miss with a `cause` from `stale_data`, `wrong_base_rate`, `misread_rules`, `missed_scheduled_event`, `overconfident`, `unlucky` or `other` and a one-line `note`, plus proposed checklist items per topic where several misses share a pattern (a lone unlucky miss proposes nothing):

   ```json
   {"reviewed_on": "2026-11-07", "summary": "Two misses were stale numbers.",
    "misses": [{"id": "polymarket-123", "cause": "stale_data", "note": "Used the headline level, not the official series."}],
    "checklist_items": {"Interest rates": ["One concrete research instruction."]}}
   ```

   `python scripts/miss_review.py apply review.json` checks it (known resolved question ids, a cause from the list, notes of one line, items of 20 to 400 characters that name no market or odds) and, only if it is valid, saves it as `data/miss_reviews/<reviewed_on>.json` (a second review that day becomes `-2`) together with what changed, and merges the new items into `configs/research_checklists.json`: duplicates are skipped, a topic keeps at most 6 items by dropping its oldest, and `version` and `updated` move on. The next research run reads the new file, because the Mac job checks out the base branch each time.

Commit the review and the checklists file together. Counting causes across the reviews (`data/miss_reviews/*.json`) shows what kind of error costs the most; whether the checklists actually help shows in the topic results of the track record, which is small and slow evidence, so treat the loop as a way to stop repeating a known mistake, not as proof of learning.
