# Architecture

ForecastLab is a local-first process, not a hosted agent mesh.

## Layout

- `packages/forecasting`: Forecast Contract compiler, Forecast Graph generator and validators, Evidence Claim extractor and context guard, structured node forecaster, graph-aware and legacy aggregators, execution engines, evaluation, providers, fetch/SSRF, Wayback eligibility, watchers.
- `apps/api`: FastAPI, SQLAlchemy, durable jobs, settings, demo indicators.
- `apps/web`: Next.js App Router UI.
- `configs/forecast_profiles`: versioned YAML profiles.
- `prompts`: versioned prompt files.
- `fixtures`: local HTML sources and synthetic benchmarks.

## Request path

1. The UI submits a natural-language question to `POST /api/contracts/generate`.
2. `QuestionCompiler` performs a vague-question preflight and uses the selected existing model seam for structured JSON. It stores a versioned `ForecastContract` as `draft`; no evidence research or forecast run begins.
3. The user reviews the outcome, resolver, deadline, and ambiguity fields. `POST /api/contracts/{id}/approve` validates the required resolution fields and changes the contract to `approved`.
4. Approval synchronizes the approved fields into the existing `ResolutionContractRow`. This compatibility projection lets the current engine consume the contract without changing provider, research-track, or aggregation behavior.
5. The UI calls `POST /api/contracts/{id}/graph`. `GraphGenerator` uses the approved contract and the selected existing model seam to produce structured research nodes. Demo mode builds the same structured shape deterministically without a provider request.
6. Validation requires the approved contract outcome as the root, at least three nodes, adversarial and resolver coverage, unique nodes, valid references, and an acyclic relationship graph. Generated output has the stricter 5–10-node requirement plus base-rate and driver coverage. Valid output is frozen as an `approved` `ForecastGraph`; invalid output is not stored.
7. `GET /api/graphs/{id}` returns the graph and nodes. A repeated generation request returns the existing approved graph rather than issuing another model request.
8. `EvidenceExtractor` accepts one fetched document plus stored evidence-item and Forecast Node identifiers. It rejects ineligible or post-cutoff documents before model extraction, requests structured claim JSON, requires each excerpt to occur in the document, and copies source metadata from the document rather than from model output.
9. Valid claims are stored in `evidence_claims`. Foreign keys require an existing `EvidenceItem` and `ForecastNode`; persistence additionally verifies cutoff flags, matching provenance, and that the evidence item and node trace to the same question.
10. `GET /api/nodes/{id}/evidence` returns the node and its claims; `GET /api/evidence/{id}` returns a full claim. The node review page displays Node → Claims → Sources and an explicit empty state.
11. `POST /api/forecasts/{id}/execute-v1` and the node-focused alias `POST /api/forecasts/{id}/node-runs` require an approved first-class contract and write a run using the `graph_forecaster_v1` profile. Neither requires the caller to pre-generate a graph. `GET /api/forecasts/{id}/node-runs` returns the latest run's node outputs. Legacy questions and profiles retain the pre-existing run path.
12. The API writes a `Job` with an idempotency key. An embedded worker may execute the same durable run inline in development and tests.
13. A worker claims the job, heartbeats, resolves the profile's execution strategy, and uses the same configured model, search, cutoff, cache, budget, and provider ledger infrastructure for either strategy.
14. For `graph_forecaster_v1`, the worker loads the latest approved contract, then loads or generates its approved graph. A newly generated graph is committed before node research. Each graph node searches and fetches documents, extracts and validates node-linked Evidence Claims, then builds a node-forecast context containing only `forecast_contract`, `node_question`, and `evidence_claims`.
15. `NodeForecaster` requires at least one eligible node-linked claim and requests a structured probability, reasoning, selected supporting and opposing claim IDs, and uncertainty notes. It rejects missing or out-of-range probabilities, malformed output, unknown claim IDs, cross-node references, and stance mismatches. Code derives the separate confidence field from cited-claim provenance quality; graph aggregation does not consume that confidence value.
16. All legacy profiles continue to execute `run_forecast_engine`: each existing track plans, searches, fetches, and forecasts without seeing other tracks. Their prompts, persisted `ResearchTrack` records, providers, and benchmark behavior are unchanged.
17. `graph_aggregation.py` applies the graph profile's fixed dependency-discounted weighted mean. It normalizes node importance weights after discounting declared dependency and parent relationships, records each node contribution, omits unavailable nodes, and renormalizes the remainder. The calculation trace and final probability are written to the existing aggregation JSON. Legacy strategies continue to use the unchanged equal-weight logit-shrinkage function.
18. Each successful graph node persists a `ForecastNodeRun` with probability, confidence, reasoning, cited claim IDs, uncertainty notes, model identity, raw importance weight, dependency factor, normalized weight, and probability contribution. `build_v1_report()` joins those rows to graph questions and Evidence Claims, separating supporting, opposing, and unselected claims while retaining source and excerpt provenance. The same structured payload drives JSON, Markdown, and the minimal report UI.
19. The standalone `GraphAggregator` accepts a frozen graph plus a complete, single-run set of node forecasts and produces `importance_weighted_log_odds_v1`. Code normalizes graph importance weights, converts each probability to log odds, sums weighted log-odds contributions, applies the logistic function, and returns a stable `ForecastAggregation` audit record. `forecast_aggregations` persists one immutable record per run. Reports understand this record, but the execution worker does not invoke the new service in this task; the currently integrated graph calculation remains unchanged.
20. The dedicated V1 evaluation endpoint freezes ten synthetic questions and the `three_track_forecaster` / `graph_forecaster_v1` pair into twenty ordinary benchmark tasks. `BenchmarkResult` stores evidence coverage plus its numerator and denominator alongside probability, Brier, log loss, cost, latency, and completion state. Benchmark graph generation and claim extraction use the experiment's stored `PromptBundle`.
21. A `ForecastVersion` is stored. Watches can mark the question stale.

## Providers

`ModelProvider.complete_json` and `SearchProvider.search` are the only model/search seams. Mock implementations satisfy the same types as the OpenAI-compatible and Tavily adapters. The shared HTTP transport may stay OpenAI-compatible while `provider_id` (`xai`, `openai`, or `openai_compatible`) is the identity used for ledger rows, `ModelUsage.provider`, pricing lookup, cost labels, provider audit output, and report execution identity. Each logical model call is reserved in memory (`budget.reserve_model_call`) before the provider adapter starts. Every physical model request reserves estimated input tokens, maximum output tokens, and both input and output estimated cost. Before every physical HTTP request, `PersistentUsageLedger` writes that reservation through a short-lived database session, checks the run-lifetime ceiling, and only then calls the provider. Timeouts, HTTP 429, and HTTP 5xx without usage keep the conservative input-plus-output reservation. Successful requests reconcile against actual usage. OpenAI-compatible and search adapters use an explicit retry loop (`run_physical_attempts`) so every physical attempt is a ledger row. Worker rollback cannot erase those rows. Retrying the same `ForecastRun` initializes `Budget` from persisted ledger totals; it does not receive a fresh full budget. `ForecastRun.cost_usd` is total lifetime cost (model + search + failed attempts). Each `ForecastRunAttempt` stores only ledger usage for its own `run_attempt_id`. ForecastLab does not claim a provider-enforced hard dollar cap.

Search and fetch caches live on one `RunCache` per forecast run. The cache is keyed to run id, model provider, search provider, mode, `as_of`, and configuration hash. A later run, including a rerun after a watch change, starts empty and fetches fresh evidence.

## Jobs

Jobs are rows, not threads. Statuses: pending, running, completed, failed. A worker claims a pending job with `UPDATE ... WHERE status='pending' RETURNING` under a SQLite write lock. Leases last 180 seconds. A background heartbeat refreshes both the job lease and `/health/worker` during long provider calls. Transient provider errors (timeouts, HTTP 429, HTTP 5xx) retry with backoff and return `rescheduled` or `exhausted`. Exhaustion marks the job, run, task, and experiment terminal. Configuration, evidence-integrity, structured-output, and other 4xx failures do not retry. Duplicate `idempotency_key` values reuse the existing job. Both legacy and graph-result persistence are idempotent on `run_id` through the unique `ForecastVersion.run_id` boundary.

A benchmark task is one durable identity for its whole lifetime, including crashes and retries:

`BenchmarkTask` → one benchmark-only `Question` → one `ForecastRun` (`forecast_runs.benchmark_task_id`, unique) → zero or one `BenchmarkResult`.

## Storage

SQLite by default. Schema types stay PostgreSQL-friendly. Secrets live in `data/local/credentials.json` and are never selected into API responses. API and worker startup inspect the current revision on a dedicated connection, skip Alembic when already at head, and otherwise upgrade under a file lock. A revision error fails closed. `20260818_0001` is a frozen explicit Alembic baseline (no live `Base.metadata.create_all()`). `20260819_0002` inspects an original MVP database and adds missing integrity columns, experiment tables, backfills, and uniqueness constraints. `20260819_0003` adds per-experiment profile snapshots, stored resolution-contract fields, and `UNIQUE(dataset_id, import_hash)`. `20260819_0004` adds `ForecastRun.benchmark_task_id`, task `question_id` / `error_category`, and `BenchmarkResult.partial`. `20260819_0005` adds run-attempt and provider-call ledger tables, run cost breakdown columns, final Wayback metadata, environment-identity columns, built-in dataset identity, and the remaining foreign keys. `20260819_0006` adds `ForecastRunAttempt.provider_request_count` so attempt totals stay attempt-specific. `20260821_0007` adds versioned `forecast_contracts` while leaving existing `resolution_contracts` and forecast rows intact. `20260821_0008` adds `forecast_graphs` and `forecast_nodes` as separate planning tables without changing existing forecast records. `20260821_0009` adds `evidence_claims` with foreign keys to existing evidence items and Forecast Nodes; no existing evidence or forecast row is rewritten. `20260822_0010` adds `forecast_node_runs`, uniquely keyed by forecast run and graph node, without rewriting legacy tracks, evidence, or forecast versions. `20260822_0011` adds confidence, raw and normalized weights, dependency factor, and contribution columns with compatibility defaults for existing node-run rows. `20260822_0012` adds nullable evidence coverage and non-null coverage-count columns to existing benchmark results with compatibility defaults. `20260822_0013` adds uncertainty-note and model-identity audit fields to node runs, with compatibility defaults for existing rows. `20260823_0014` adds immutable `forecast_aggregations`, uniquely keyed by forecast run, with stored node contributions and calculation trace. The existing execution aggregation JSON remains intact for compatibility. Isolated unit tests may still call `create_all`. Fresh empty→head and original-MVP→head databases must match on tables, columns, nullability, keys, and indexes, allowing only the documented SQLite representation differences. `PRAGMA foreign_key_check` must be empty. Back up `data/forecastlab.db` before the first launch after an upgrade (`cp data/forecastlab.db data/forecastlab.db.bak`). Do not treat the local database as a production cluster.

SQLite strips timezone info on read. Health checks, watch polling, and latency math always run datetimes through `as_utc`.

## Request commit timing

FastAPI dependencies that `yield` a session commit *after* the HTTP response is sent. Write endpoints therefore call `db.commit()` before returning so a follow-up operationalize or worker claim can see the row.

## UI proxy

The Next.js app calls relative `/api/...` and `/demo/...` routes. Catch-all App Router handlers forward those requests to `FORECASTLAB_API_ORIGIN` (default `http://127.0.0.1:8765`) so the browser does not depend on cross-origin access to the API port. Docker Compose sets `FORECASTLAB_API_ORIGIN=http://api:8765` on the web service.

## Version and Python lock

Application version `0.3.1` lives in `packages/forecasting/forecastlab/version.py`. The Python package, FastAPI app, frozen environment identity, `/health`, `/api/meta`, and the Lab nav derive from that file. Real experiments require a committed `uv.lock` (or `poetry.lock`) hash. Synthetic experiments may still run when explicitly marked synthetic. Local scripts, GitHub Actions, and Docker Compose install from that lockfile instead of resolving broad minimum versions on every run.
