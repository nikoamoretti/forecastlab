# Architecture

ForecastLab is a local-first process, not a hosted agent mesh.

## Layout

- `packages/forecasting`: Forecast Contract compiler, Forecast Graph generator and validators, Evidence Claim extractor and context guard, deterministic evidence-sufficiency evaluator, structured node forecaster, graph-aware and legacy aggregators, execution engines, evaluation, providers, fetch/SSRF, Wayback eligibility, watchers.
- `apps/api`: FastAPI, SQLAlchemy, durable jobs, settings, demo indicators.
- `apps/web`: Next.js App Router UI.
- `configs/forecast_profiles`: versioned YAML profiles.
- `prompts`: versioned prompt files.
- `fixtures`: local HTML sources and synthetic benchmarks.

## Request path

1. The UI submits a natural-language question to `POST /api/contracts/generate`.
2. `QuestionCompiler` performs a vague-question preflight and uses the selected existing model seam for structured JSON. It stores a versioned `ForecastContract` as `draft`; no evidence research or forecast run begins.
3. The user reviews the outcome, resolver, deadline, and ambiguity fields. `POST /api/contracts/{id}/approve` validates the required resolution fields and changes the contract to `approved`.
4. Approval synchronizes the approved fields into the existing `ResolutionContractRow`. This compatibility projection lets the current engine consume the contract without changing provider, research-track, or aggregation behavior.
5. The UI calls `POST /api/contracts/{id}/graph`. `GraphGenerator` uses the approved contract and the selected existing model seam to produce structured research nodes and returns a typed result containing the graph plus a sanitized generation audit. The active Forecast Profile's `max_output_tokens_per_call` is passed explicitly from graph execution through graph resolution and generation to the provider; graph generation has no private 4,096-token override. For supported OpenAI models, graph output uses a strict JSON Schema with the 5–10 node bound, typed enums, and bounded weights. The V3 smoke profile uses the compact indexed wire transport `compact_indexed_v1`: the provider emits only compact node values and integer relationships, after which ForecastLab deterministically restores local IDs, canonical field names, and pending status before running every existing graph-domain validation and approval rule. GPT-5 graph generation requests minimal reasoning effort. Demo mode builds the same canonical graph deterministically without a provider request.
6. Validation requires the approved contract outcome as the root, at least three nodes, adversarial and resolver coverage, unique nodes, valid references, and an acyclic relationship graph. Generated output has the stricter 5–10-node requirement plus base-rate and driver coverage. Valid output is frozen as an `approved` `ForecastGraph`; invalid output is not stored.
7. `GET /api/graphs/{id}` returns the graph and nodes. A repeated generation request returns the existing approved graph rather than issuing another model request.
8. `EvidenceExtractor` accepts one fetched document plus stored evidence-item and Forecast Node identifiers. It validates temporal provenance before model extraction, requests structured claim JSON, requires each excerpt to occur in the document, and copies source metadata from the document rather than from model output. Publication time and proven source-availability time are separate fields. In live mode, an undated page may use the run's retrieval timestamp as proof that the content-hashed page was observed during that run; its publication date stays null. In backtest mode, retrieval time is never eligible and a verified final archive snapshot or explicitly supported immutable historical timestamp must establish availability at or before the cutoff. The execution branch deterministically records `source_class`, `extraction_method`, and normalized `source_host`; model-authored confidence, source-quality, and primary-source labels do not control the private-V1 sufficiency gate.
9. Valid claims are stored in `evidence_claims`. Foreign keys require an existing `EvidenceItem` and `ForecastNode`; persistence additionally verifies cutoff flags, matching temporal and content provenance, and that the evidence item and node trace to the same question. Legacy claims are conservatively marked `unknown_legacy` unless source class or host can be recovered deterministically; legacy extraction method is never invented.
10. `GET /api/nodes/{id}/evidence` returns the node and its claims; `GET /api/evidence/{id}` returns a full claim. The node review page displays Node → Claims → Sources and an explicit empty state.
11. `POST /api/forecasts/{id}/execute-graph` starts the complete graph path, and `GET /api/forecasts/{id}/graph-report` returns its audit report for the actual graph profile that ran. The existing V1 and node-run endpoints remain available. Every graph entry point requires an approved first-class contract; callers do not need to pre-generate a graph. Legacy questions and profiles retain the pre-existing run path. `graph_forecaster_v1` remains the production/evaluation architecture profile. The separate `graph_live_smoke_v1` profile selects the same executor, Research Planner, prompts, and aggregation method with a tightly bounded operational workload; it is not in either scientific evaluation allowlist.
12. Successful graph generation persists only sanitized diagnostics on the immutable graph row: provider/model, schema and request identity, profile-controlled completion and visible-output envelopes, reasoning effort and verbosity, finish/refusal state, reported completion/reasoning/visible token counts, the conservative interpretation used when a token split is unavailable, content character count, parse/schema/domain-validation results, prompt version, errors, and timestamp. Response content, reasoning content, prompts, headers, authorization material, and credentials are excluded. A run records the graph ID/version, `generated` or `reused` status, whether that run issued a graph-model request, and the exact persisted audit. Reuse issues no graph-generation request and does not fabricate missing audit history for legacy graphs.
13. The API writes a `Job` with an idempotency key. An embedded worker may execute the same durable run inline in development and tests.
14. A worker claims the job, heartbeats, resolves the profile's execution strategy, and uses the same configured model, search, cutoff, cache, budget, and provider ledger infrastructure for every strategy.
15. For version 6 of `graph_forecaster_v1`, `GraphForecastExecutor` loads the latest approved contract, then loads or generates its approved graph. A newly generated graph is committed before node research. Research Planner V3 (`graph_research_planner_v3`) preserves the V2 priority formula and forecast-call reservation while separating target successful documents from distinct candidate URL attempts. Model extraction and bounded smaller-chunk retry calls scale with the successful-document target; physical fetch allowance scales with candidate attempts. A selected node searches once under the bounded smoke profile and retains a frozen candidate pool. It deterministically ranks and canonicalizes candidates, keeps the top-ranked URL first, then schedules the best relevant distinct hosts before another URL from a previously scheduled host. HTTP 401, 403, and 451 block that hostname for only that node; remaining same-host URLs are audited and skipped without consuming another physical fetch attempt. No URL is retried, no backup search is issued, and every distinct-host alternate still passes the ordinary safety, provenance, temporal, extraction, and evidence rules. The immutable plan records targets, pool size, host-diversity policy, candidate/backup attempts, per-phase calls/tokens/cost, graph envelopes, selected breadth, skipped reasons/order, forecast reserve, and post-plan headroom. Sanitized per-candidate returned/ranked/scheduled positions, canonical URL, normalized host, query, outcome, block/skip state, backup use, extraction entry, claim creation, HTTP status, and elapsed fetch time are retained in the run execution audit; response bodies are not.
16. Before selected nodes research concurrently through independent caches, the shared thread-safe `Budget` freezes role-specific logical-call quotas and reserves one node-forecast call per selected node. Research-plan, primary-extraction, and bounded retry calls cannot consume that forecast capacity or exceed their persisted phase quotas, even when workers race. `GraphResearchExecutor` also enforces each node's own allocation: it can use a smaller-chunk retry only when that retry was planned, otherwise it proceeds directly to the existing zero-model-call document fallback. Unused retry or forecast reservations remain visible as unused plan capacity and never become provider or ledger usage. Evidence and node outputs are persisted afterward in deterministic dependency order. Skipped nodes and reasons remain in the immutable plan and report; they are not treated as execution failures or aggregation inputs.
17. `NodeForecaster` requires at least one eligible node-linked claim and requests a structured probability, reasoning, selected supporting and opposing claim IDs, and uncertainty notes. It rejects missing or out-of-range probabilities, malformed output, unknown claim IDs, cross-node references, and stance mismatches. Code derives the separate confidence field from cited-claim provenance quality; graph aggregation does not consume that confidence value.
18. `single_model_forecaster_v1` selects an isolated `single_model` strategy. Code derives one deterministic search query from the approved Forecast Contract, builds one provenance-bearing evidence packet, and makes exactly one structured forecasting call. The model receives the contract plus excerpts and returns probability, reasoning, uncertainty, and selected evidence IDs. The direct probability is stored through the normal `ForecastVersion` compatibility boundary with method `direct_model_probability_v1`; no Forecast Graph, Evidence Claim, node forecast, or probability aggregation service is created or invoked.
19. All legacy profiles continue to execute `run_forecast_engine`: each existing track plans, searches, fetches, and forecasts without seeing other tracks. Their prompts, persisted `ResearchTrack` records, providers, and benchmark behavior are unchanged.
20. Each successful selected graph node becomes a `ForecastNodeRun` with probability, confidence, reasoning, cited claim IDs, uncertainty notes, model identity, raw importance weight, and normalized weight. A failed node records its research plan, attempted queries, checked sources, structured failure code, criticality, and forecast impact. Nodes with importance weight at least `0.8` are critical. A critical failure, or fewer than three successful nodes, fails the forecast. Other failed nodes are excluded with an explicit reduced-confidence audit record.
21. Production profile v6 evaluates `private_v1_evidence_gate_v1` after the existing critical/minimum-node policy and immediately before aggregation. The pure evaluator counts only eligible claims actually cited by included node runs and uses deterministic source class, extraction method, normalized host, item identity, node linkage, temporal eligibility, and canonical graph weights. It ignores forecast probabilities, resolved outcomes, and model-authored quality/confidence labels. The frozen policy requires at least three included node forecasts, at least two-thirds selected-node coverage, at least 0.50 graph-importance coverage, structured evidence for every included node, stronger evidence for every selected critical node, at least one included node with structured primary evidence, and at least two distinct cited hosts. Fallback-only and `unknown_legacy` evidence cannot satisfy the gate.
22. One immutable `EvidenceSufficiencyAssessment` per run stores the policy snapshot, deterministic input hash, stable reasons and warnings, counts and exact coverage values, included/excluded/insufficient node IDs, and per-node grades. Re-evaluating identical inputs returns the existing row; a changed input hash is a persistence-integrity failure. A failed assessment preserves research, claims, and node forecasts, marks stage `evidence_sufficiency` with code `evidence_sufficiency_gate_failed`, and creates no aggregation, Forecast Version, or probability. `graph_live_smoke_v1` version 3 has no sufficiency policy and keeps its operational-smoke behavior unchanged.
23. `GraphAggregator` accepts the complete set of successful node forecasts for the eligible graph subset and produces the unchanged `importance_weighted_log_odds_v1` calculation. Code normalizes the included importance weights, converts probabilities to log odds, sums signed weighted log-odds contributions, applies the logistic function, and returns a stable `ForecastAggregation`. A passing production assessment ID, policy, and hash are prepended to the calculation trace without changing the math. `forecast_aggregations` stores one immutable record per run.
24. The executor persists node runs, structured failures, the sufficiency assessment when configured, the Forecast Aggregation, and the Forecast Version as the final success boundary. Critical graph, research, node, evidence-sufficiency, or aggregation failures retain completed work but create neither an aggregation nor a Forecast Version. Tolerated noncritical failures remain visible and never receive an imputed probability.
25. `build_v1_report()` joins the contract, Research Plan, graph, node runs, Evidence Claims, execution failures, Evidence Sufficiency Assessment, and Forecast Aggregation. It separates selected, skipped, supporting, opposing, and unselected records while retaining source, excerpt, publication, retrieval, source-availability, temporal-basis, cutoff, deterministic source-class, extraction-method, and host provenance. Reports visibly distinguish verified publication dates, verified historical snapshots, live pages observed during the run, and evidence-sufficiency failure. A failed private-V1 gate shows a null final probability and explains that deterministic sufficiency was not met. The same structured payload drives JSON, Markdown, and the minimal report UI.
26. The dedicated V1 evaluation endpoint freezes ten synthetic questions and `single_model_forecaster_v1`, `three_track_forecaster`, and `graph_forecaster_v1` into thirty ordinary benchmark tasks. The three profiles receive equivalent question and contract content, the same cutoff, evidence policy, provider identity, and equal total resource ceilings. `BenchmarkResult` stores evidence coverage plus its numerator and denominator alongside probability, Brier, log loss, cost, latency, and completion state. Benchmark graph generation and claim extraction use the experiment's stored `PromptBundle`. Synthetic graph cells can now fail the production sufficiency gate; such failures remain unscored rather than receiving a fixture-only bypass.
27. Real resolved evaluation data uses separate `EvaluationDataset` and `EvaluationQuestion` tables. CSV or JSON import validates every row atomically and creates a `draft`; explicit review revalidates and re-hashes the release, and freeze succeeds only when the reviewed contents remain unchanged. Frozen releases are immutable and corrections require a new version.
28. `ForecastExperiment` connects a frozen real-evaluation release to the exact controlled profile set: `single_model_forecaster_v1`, `three_track_forecaster`, and `graph_forecaster_v1`. Its canonical configuration stores the dataset and question snapshots, effective profiles and equal ceilings, public provider/model metadata, complete prompt bundle, pricing, and code/dependency identity. Secret values are excluded and frozen fields cannot be updated.
29. Creation writes one durable `ForecastExperimentRun` and job for every question/profile cell. The worker reconstructs the stored profile, prompt bundle, and `ExecutionContext`, projects the frozen resolution rule into compatibility Question and approved Forecast Contract records, and calls the existing execution strategy unchanged. Dataset or environment drift fails closed.
30. `ForecastExperimentResult` stores the cell probability and resolved outcome, Brier score, log loss, cost, latency, evidence coverage, and completion state. Failed cells preserve their errors and cost but no synthetic probability. The report exposes the question-level rows and a three-profile comparison table with an explicit measurement-only claim boundary.
31. The read-only forecast analysis builder joins those controlled results to accepted evidence items, eligible Evidence Claims, and internal `ForecastFailure` annotations. It pairs completed results by identical evaluation-question identity for the three fixed profile comparisons, computes profile-A-minus-profile-B Brier and log-loss differences, and returns deterministic 95% paired percentile-bootstrap intervals using 2,000 samples and seed `20260823`. Intervals are withheld below 20 paired questions as `insufficient evidence`. The same response includes five fixed calibration buckets per profile, cost-efficiency ratios, cost and latency differences, failures, evidence coverage, claim counts, and existing source-quality measurements. The flat failure taxonomy covers contract, evidence, decomposition, node forecast, aggregation, and operational mechanisms. Analysis is derived from stored experiment rows, requires no schema migration, does not call the forecasting pipeline, and never updates a forecast result.
32. A successful execution stores a `ForecastVersion`. Watches can mark the question stale.

## Providers

`ModelProvider.complete_json` and `SearchProvider.search` are the only model/search seams. Mock implementations satisfy the same types as the OpenAI-compatible and Tavily adapters. The shared HTTP transport may stay OpenAI-compatible while `provider_id` (`xai`, `openai`, or `openai_compatible`) is the identity used for ledger rows, `ModelUsage.provider`, pricing lookup, cost labels, provider audit output, and report execution identity. Each logical model call is reserved in memory (`budget.reserve_model_call`) before the provider adapter starts. Graph planning's logical-call envelope is separate from physical HTTP retry accounting: one planned logical call may have multiple ledgered physical attempts under the existing retry policy, but physical retries never create additional planner capacity. Every physical model request reserves estimated input tokens, maximum output tokens, and both input and output estimated cost. Before every physical HTTP request, `PersistentUsageLedger` writes that reservation through a short-lived database session, checks the run-lifetime ceiling, and only then calls the provider. Timeouts, HTTP 429, and HTTP 5xx without usage keep the conservative input-plus-output reservation. Successful requests reconcile against actual usage. OpenAI-compatible and search adapters use an explicit retry loop (`run_physical_attempts`) so every physical attempt is a ledger row. Worker rollback cannot erase those rows. Retrying the same `ForecastRun` initializes `Budget` from persisted ledger totals; it does not receive a fresh full budget. `ForecastRun.cost_usd` is total lifetime cost (model + search + failed attempts). Each `ForecastRunAttempt` stores only ledger usage for its own `run_attempt_id`. ForecastLab does not claim a provider-enforced hard dollar cap.

Strict OpenAI JSON-schema behavior is capability-gated to the `openai` identity; xAI and generic compatible providers retain their existing JSON-object request shape unless separately declared capable. The version 3 operational smoke profile gives GPT-5 graph generation an 8,192-token total completion/reasoning envelope while retaining a separately enforced 1,536-token visible Forecast Graph JSON cap, minimal reasoning, and low verbosity. Its strict compact indexed transport also caps serialized provider output at 4,200 characters, node questions at 140 characters, dependency indexes at three, and preferred-source guidance at two 48-character strings. The raw visible-token and character guards run before canonical conversion; invalid, oversized, or cyclic output fails without truncation, repair, or another request. The complete envelope is reserved and reconciled against the unchanged run token and cost ceilings. Unsupported provider identities fail before a request rather than receiving OpenAI-only fields. For graph responses, HTTP transport success, JSON/schema success, transport-budget success, canonical graph-domain success, and approval are separate states. Sanitized audit metadata records schema/transport, request ID, finish reason, refusal category, both requested envelopes, reasoning/verbosity settings, completion/reasoning/visible token counts and split interpretation, content and compact-transport character counts, and parse/schema outcomes without response content, raw headers, authorization data, or reasoning content. Truncation, visible-budget excess, transport-character excess, refusal, empty output, invalid JSON, schema mismatch, and domain-validation failure have distinct fail-closed codes. None triggers an automatic graph repair or graph-generation retry.

Before a non-synthetic live or backtest run is created, launch preflight computes a model upper bound from the profile token limit and frozen pricing catalog, a search upper bound from planned search calls times the effective search provider's per-request estimate, and their total. The total, rather than the model component alone, is compared with the effective Settings/profile ceiling. Missing model or search pricing is exposed as unavailable and fails closed. The complete breakdown is part of `ExecutionContext`, so successful execution previews and stored run JSON expose the same figures without a schema migration; rejected previews and launch responses return it as structured preflight detail.

Search and fetch caches live on one `RunCache` per forecast run. The cache is keyed to run id, model provider, search provider, mode, `as_of`, and configuration hash. A later run, including a rerun after a watch change, starts empty and fetches fresh evidence.

## Jobs

Jobs are rows, not threads. Statuses: pending, running, completed, failed. A worker claims a pending job with `UPDATE ... WHERE status='pending' RETURNING` under a SQLite write lock. Leases last 180 seconds. A background heartbeat refreshes both the job lease and `/health/worker` during long provider calls. Transient provider errors (timeouts, HTTP 429, HTTP 5xx) retry with backoff and return `rescheduled` or `exhausted`. Exhaustion marks the job, run, task, and experiment terminal. Configuration, evidence-integrity, structured-output, and other 4xx failures do not retry. Duplicate `idempotency_key` values reuse the existing job. Both legacy and graph-result persistence are idempotent on `run_id` through the unique `ForecastVersion.run_id` boundary.

A benchmark task is one durable identity for its whole lifetime, including crashes and retries:

`BenchmarkTask` → one benchmark-only `Question` → one `ForecastRun` (`forecast_runs.benchmark_task_id`, unique) → zero or one `BenchmarkResult`.

The controlled real-dataset equivalent is:

`ForecastExperimentRun` → one compatibility `Question` → one `ForecastRun` (`forecast_experiment_runs.forecast_run_id`, unique) → one terminal `ForecastExperimentResult`.

## Storage

SQLite by default. Schema types stay PostgreSQL-friendly. Secrets live in `data/local/credentials.json` and are never selected into API responses. API and worker startup inspect the current revision on a dedicated connection, skip Alembic when already at head, and otherwise upgrade under a file lock. no existing evidence or forecast row is rewritten. `20260822_0010` adds `forecast_node_runs`, uniquely keyed by forecast run and graph node, without rewriting legacy tracks, evidence, or forecast versions. `20260822_0011` adds confidence, raw and normalized weights, dependency factor, and contribution columns with compatibility defaults for existing node-run rows. `20260822_0012` adds nullable evidence coverage and non-null coverage-count columns to existing benchmark results with compatibility defaults. `20260822_0013` adds uncertainty-note and model-identity audit fields to node runs, with compatibility defaults for existing rows. `20260823_0014` adds immutable `forecast_aggregations`, uniquely keyed by forecast run, with stored node contributions and calculation trace. `20260823_0015` adds durable `graph_execution_failures` with run, optional node, stage, code, and message fields. `20260823_0016` adds versioned real `evaluation_datasets` and resolved `evaluation_questions` without rewriting existing forecast or benchmark records. `20260823_0017` adds controlled `forecast_experiments`, `forecast_experiment_runs`, and `forecast_experiment_results`, linked to but not rewriting the frozen dataset and existing forecast records. `20260823_0018` adds internal `forecast_failures` linked to controlled runs, without changing any stored forecast probability or result. The existing execution aggregation JSON remains intact for compatibility. Isolated unit tests may still call `create_all`. Fresh empty-to-head and original-MVP-to-head databases must match on tables, columns, nullability, keys, and indexes, allowing only the documented SQLite representation differences. `PRAGMA foreign_key_check` must be empty. Existing rows remain `NULL`, so previously frozen question and dataset hashes are preserved. Migration `20260823_0020` adds research-plan, query, source-check, criticality, and impact audit fields to graph execution failures without rewriting existing failure or forecast records. Migration `20260824_0021` adds one immutable `research_plans` row per Forecast Run, including selected and skipped node IDs, priority scores, budget allocation, and creation time; existing runs and forecast records are unchanged. Migration `20260825_0022` separates optional publication time from required retrieval and source-availability timestamps on evidence items and claims, records the typed temporal basis and publication-verification state, preserves existing publication dates, and honestly backfills legacy availability without relabeling retrieval time as publication time. Migration `20260825_0023` adds the nullable successful graph-generation audit document; existing graph rows remain `NULL` so the migration does not fabricate unavailable history. Migration `20260826_0024` adds deterministic claim source class, extraction method, normalized source host, and one immutable evidence-sufficiency assessment per run. It preserves all prior claim content and temporal fields, backfills only deterministically recoverable source class/host values, and labels unrecoverable history `unknown_legacy` rather than fabricating structured provenance. SQLite strips timezone info on read. Health checks, watch polling, and latency math always run datetimes through `as_utc`.

## Request commit timing

FastAPI dependencies that `yield` a session commit *after* the HTTP response is sent. Write endpoints therefore call `db.commit()` before returning so a follow-up operationalize or worker claim can see the row.

## UI proxy

The Next.js app calls relative `/api/...` and `/demo/...` routes. Catch-all App Router handlers forward those requests to `FORECASTLAB_API_ORIGIN` (default `http://127.0.0.1:8765`) so the browser does not depend on cross-origin access to the API port. Docker Compose sets `FORECASTLAB_API_ORIGIN=http://api:8765` on the web service.

## Version and Python lock

Application version `0.3.1` lives in `packages/forecasting/forecastlab/version.py`. The Python package, FastAPI app, frozen environment identity, `/health`, `/api/meta`, and the Lab nav derive from that file. Real experiments require a committed `uv.lock` (or `poetry.lock`) hash. Synthetic experiments may still run when explicitly marked synthetic. Local scripts, GitHub Actions, and Docker Compose install from that lockfile instead of resolving broad minimum versions on every run.
