# Architecture

ForecastLab is a local-first process, not a hosted agent mesh.

## Layout

- `packages/forecasting`: Forecast Contract compiler, Forecast Graph generator and validators, Evidence Claim extractor and context guard, structured node forecaster, graph-aware and legacy aggregators, execution engines, evaluation, providers, fetch/SSRF, Wayback eligibility, watchers.
- `apps/api`: FastAPI, SQLAlchemy, durable jobs, settings, demo indicators.
- `apps/web`: Next.js App Router UI.
- `configs/forecast_profiles`: versioned YAML profiles.
- `prompts`: versioned prompt files.
- `fixtures`: local HTML sources and synthetic benchmarks.

## Request path

1. The UI submits a natural-language question to `POST /api/contracts/generate`.
2. `QuestionCompiler` performs a vague-question preflight and uses the selected existing model seam for structured JSON. It stores a versioned `ForecastContract` as `draft`; no evidence research or forecast run begins.
3. The user reviews the outcome, resolver, deadline, and ambiguity fields. `POST /api/contracts/{id}/approve` validates the required resolution fields and changes the contract to `approved`.
4. Approval synchronizes the approved fields into the existing `ResolutionContractRow`. This compatibility projection lets the current engine consume the contract without changing provider, research-track, or aggregation behavior.
5. The UI calls `POST /api/contracts/{id}/graph`. `GraphGenerator` uses the approved contract and the selected existing model seam to produce structured research nodes. Demo mode builds the same structured shape deterministically without a provider request.
6. Validation requires the approved contract outcome as the root, at least three nodes, adversarial and resolver coverage, unique nodes, valid references, and an acyclic relationship graph. Generated output has the stricter 5–10-node requirement plus base-rate and driver coverage. Valid output is frozen as an `approved` `ForecastGraph`; invalid output is not stored.
7. `GET /api/graphs/{id}` returns the graph and nodes. A repeated generation request returns the existing approved graph rather than issuing another model request.
8. `EvidenceExtractor` accepts one fetched document plus stored evidence-item and Forecast Node identifiers. It rejects ineligible or post-cutoff documents before model extraction, requests structured claim JSON, requires each excerpt to occur in the document, and copies source metadata from the document rather than from model output.
9. Valid claims are stored in `evidence_claims`. Foreign keys require an existing `EvidenceItem` and `ForecastNode`; persistence additionally verifies cutoff flags, matching provenance, and that the evidence item and node trace to the same question.
10. `GET /api/nodes/{id}/evidence` returns the node and its claims; `GET /api/evidence/{id}` returns a full claim. The node review page displays Node → Claims → Sources and an explicit empty state.
11. `POST /api/forecasts/{id}/execute-graph` starts the complete `graph_forecaster_v1` path, and `GET /api/forecasts/{id}/graph-report` returns its audit report. The existing V1 and node-run endpoints remain available. Every graph entry point requires an approved first-class contract; callers do not need to pre-generate a graph. Legacy questions and profiles retain the pre-existing run path. `graph_forecaster_v1` remains the production/evaluation architecture profile. The separate `graph_live_smoke_v1` profile selects the same executor, Research Planner, prompts, and aggregation method with a tightly bounded operational workload; it is not in either scientific evaluation allowlist.
12. The API writes a `Job` with an idempotency key. An embedded worker may execute the same durable run inline in development and tests.
13. A worker claims the job, heartbeats, resolves the profile's execution strategy, and uses the same configured model, search, cutoff, cache, budget, and provider ledger infrastructure for every strategy.
14. For version 5 of `graph_forecaster_v1`, `GraphForecastExecutor` loads the latest approved contract, then loads or generates its approved graph. A newly generated graph is committed before node research. `ResearchPlanner` ranks nodes by importance, graph dependency count, and a deterministic node-type uncertainty score; always includes critical nodes; and freezes a `ResearchPlan` before provider execution. It selects no more than eight nodes, five searches per node, or twenty claims total, reduces the set when the remaining call/token/cost/time budget cannot support it, and fails before research when the critical or minimum set cannot finish within those estimates.
15. Selected nodes research concurrently through independent caches and one thread-safe run budget. `GraphResearchExecutor` bounds extraction input to the plan's resource tier, tries a smaller chunk after extraction failure, then creates a low-confidence verbatim document fallback claim when provenance and cutoff checks still pass. Evidence and node outputs are persisted afterward in deterministic dependency order. Skipped nodes and reasons remain in the immutable plan and report; they are not treated as execution failures or aggregation inputs.
16. `NodeForecaster` requires at least one eligible node-linked claim and requests a structured probability, reasoning, selected supporting and opposing claim IDs, and uncertainty notes. It rejects missing or out-of-range probabilities, malformed output, unknown claim IDs, cross-node references, and stance mismatches. Code derives the separate confidence field from cited-claim provenance quality; graph aggregation does not consume that confidence value.
17. `single_model_forecaster_v1` selects an isolated `single_model` strategy. Code derives one deterministic search query from the approved Forecast Contract, builds one provenance-bearing evidence packet, and makes exactly one structured forecasting call. The model receives the contract plus excerpts and returns probability, reasoning, uncertainty, and selected evidence IDs. The direct probability is stored through the normal `ForecastVersion` compatibility boundary with method `direct_model_probability_v1`; no Forecast Graph, Evidence Claim, node forecast, or probability aggregation service is created or invoked.
18. All legacy profiles continue to execute `run_forecast_engine`: each existing track plans, searches, fetches, and forecasts without seeing other tracks. Their prompts, persisted `ResearchTrack` records, providers, and benchmark behavior are unchanged.
19. Each successful selected graph node becomes a `ForecastNodeRun` with probability, confidence, reasoning, cited claim IDs, uncertainty notes, model identity, raw importance weight, and normalized weight. A failed node records its research plan, attempted queries, checked sources, structured failure code, criticality, and forecast impact. Nodes with importance weight at least `0.8` are critical. A critical failure, or fewer than three successful nodes, fails the forecast. Other failed nodes are excluded with an explicit reduced-confidence audit record.
20. `GraphAggregator` accepts the complete set of successful node forecasts for the eligible graph subset and produces the unchanged `importance_weighted_log_odds_v1` calculation. Code normalizes the included importance weights, converts probabilities to log odds, sums signed weighted log-odds contributions, applies the logistic function, and returns a stable `ForecastAggregation`. The calculation trace records any exclusion before the existing mathematical steps. `forecast_aggregations` stores one immutable record per run.
21. The executor persists node runs, structured failures, the Forecast Aggregation, and the Forecast Version as the final success boundary. Critical graph, research, node, or aggregation failures retain partial work but create neither an aggregation nor a Forecast Version. Tolerated noncritical failures remain visible on an otherwise completed run and never receive an imputed probability.
22. `build_v1_report()` joins the contract, Research Plan, graph, node runs, Evidence Claims, execution failures, and Forecast Aggregation. It separates selected, skipped, supporting, opposing, and unselected records while retaining source and excerpt provenance, shows the exact calculation and final answer, and labels reduced research coverage. The same structured payload drives JSON, Markdown, and the minimal report UI.
23. The dedicated V1 evaluation endpoint freezes ten synthetic questions and `single_model_forecaster_v1`, `three_track_forecaster`, and `graph_forecaster_v1` into thirty ordinary benchmark tasks. The three profiles receive equivalent question and contract content, the same cutoff, evidence policy, provider identity, and equal total resource ceilings. `BenchmarkResult` stores evidence coverage plus its numerator and denominator alongside probability, Brier, log loss, cost, latency, and completion state. Benchmark graph generation and claim extraction use the experiment's stored `PromptBundle`.
24. Real resolved evaluation data uses separate `EvaluationDataset` and `EvaluationQuestion` tables. CSV or JSON import validates every row atomically and creates a `draft`; explicit review revalidates and re-hashes the release, and freeze succeeds only when the reviewed contents remain unchanged. Frozen releases are immutable and corrections require a new version.
25. `ForecastExperiment` connects a frozen real-evaluation release to the exact controlled profile set: `single_model_forecaster_v1`, `three_track_forecaster`, and `graph_forecaster_v1`. Its canonical configuration stores the dataset and question snapshots, effective profiles and equal ceilings, public provider/model metadata, complete prompt bundle, pricing, and code/dependency identity. Secret values are excluded and frozen fields cannot be updated.
26. Creation writes one durable `ForecastExperimentRun` and job for every question/profile cell. The worker reconstructs the stored profile, prompt bundle, and `ExecutionContext`, projects the frozen resolution rule into compatibility Question and approved Forecast Contract records, and calls the existing execution strategy unchanged. Dataset or environment drift fails closed.
27. `ForecastExperimentResult` stores the cell probability and resolved outcome, Brier score, log loss, cost, latency, evidence coverage, and completion state. Failed cells preserve their errors and cost but no synthetic probability. The report exposes the question-level rows and a three-profile comparison table with an explicit measurement-only claim boundary.
28. The read-only forecast analysis builder joins those controlled results to accepted evidence items, eligible Evidence Claims, and internal `ForecastFailure` annotations. It pairs completed results by identical evaluation-question identity for the three fixed profile comparisons, computes profile-A-minus-profile-B Brier and log-loss differences, and returns deterministic 95% paired percentile-bootstrap intervals using 2,000 samples and seed `20260823`. Intervals are withheld below 20 paired questions as `insufficient evidence`. The same response includes five fixed calibration buckets per profile, cost-efficiency ratios, cost and latency differences, failures, evidence coverage, claim counts, and existing source-quality measurements. The flat failure taxonomy covers contract, evidence, decomposition, node forecast, aggregation, and operational mechanisms. Analysis is derived from stored experiment rows, requires no schema migration, does not call the forecasting pipeline, and never updates a forecast result.
29. A successful execution stores a `ForecastVersion`. Watches can mark the question stale.

## Providers

`ModelProvider.complete_json` and `SearchProvider.search` are the only model/search seams. Mock implementations satisfy the same types as the OpenAI-compatible and Tavily adapters. The shared HTTP transport may stay OpenAI-compatible while `provider_id` (`xai`, `openai`, or `openai_compatible`) is the identity used for ledger rows, `ModelUsage.provider`, pricing lookup, cost labels, provider audit output, and report execution identity. Each logical model call is reserved in memory (`budget.reserve_model_call`) before the provider adapter starts. Every physical model request reserves estimated input tokens, maximum output tokens, and both input and output estimated cost. Before every physical HTTP request, `PersistentUsageLedger` writes that reservation through a short-lived database session, checks the run-lifetime ceiling, and only then calls the provider. Timeouts, HTTP 429, and HTTP 5xx without usage keep the conservative input-plus-output reservation. Successful requests reconcile against actual usage. OpenAI-compatible and search adapters use an explicit retry loop (`run_physical_attempts`) so every physical attempt is a ledger row. Worker rollback cannot erase those rows. Retrying the same `ForecastRun` initializes `Budget` from persisted ledger totals; it does not receive a fresh full budget. `ForecastRun.cost_usd` is total lifetime cost (model + search + failed attempts). Each `ForecastRunAttempt` stores only ledger usage for its own `run_attempt_id`. ForecastLab does not claim a provider-enforced hard dollar cap.

Before a non-synthetic live or backtest run is created, launch preflight computes a model upper bound from the profile token limit and frozen pricing catalog, a search upper bound from planned search calls times the effective search provider's per-request estimate, and their total. The total, rather than the model component alone, is compared with the effective Settings/profile ceiling. Missing model or search pricing is exposed as unavailable and fails closed. The complete breakdown is part of `ExecutionContext`, so successful execution previews and stored run JSON expose the same figures without a schema migration; rejected previews and launch responses return it as structured preflight detail.

Search and fetch caches live on one `RunCache` per forecast run. The cache is keyed to run id, model provider, search provider, mode, `as_of`, and configuration hash. A later run, including a rerun after a watch change, starts empty and fetches fresh evidence.

## Jobs

Jobs are rows, not threads. Statuses: pending, running, completed, failed. A worker claims a pending job with `UPDATE ... WHERE status='pending' RETURNING` under a SQLite write lock. Leases last 180 seconds. A background heartbeat refreshes both the job lease and `/health/worker` during long provider calls. Transient provider errors (timeouts, HTTP 429, HTTP 5xx) retry with backoff and return `rescheduled` or `exhausted`. Exhaustion marks the job, run, task, and experiment terminal. Configuration, evidence-integrity, structured-output, and other 4xx failures do not retry. Duplicate `idempotency_key` values reuse the existing job. Both legacy and graph-result persistence are idempotent on `run_id` through the unique `ForecastVersion.run_id` boundary.

A benchmark task is one durable identity for its whole lifetime, including crashes and retries:

`BenchmarkTask` → one benchmark-only `Question` → one `ForecastRun` (`forecast_runs.benchmark_task_id`, unique) → zero or one `BenchmarkResult`.

The controlled real-dataset equivalent is:

`ForecastExperimentRun` → one compatibility `Question` → one `ForecastRun` (`forecast_experiment_runs.forecast_run_id`, unique) → one terminal `ForecastExperimentResult`.

## Storage

SQLite by default. Schema types stay PostgreSQL-friendly. Secrets live in `data/local/credentials.json` and are never selected into API responses. API and worker startup inspect the current revision on a dedicated connection, skip Alembic when already at head, and otherwise upgrade under a file lock. A revision error fails closed. `20260818_0001` is a frozen explicit Alembic baseline (no live `Base.metadata.create_all()`). `20260819_0002` inspects an original MVP database and adds missing integrity columns, experiment tables, backfills, and uniqueness constraints. `20260819_0003` adds per-experiment profile snapshots, stored resolution-contract fields, and `UNIQUE(dataset_id, import_hash)`. `20260819_0004` adds `ForecastRun.benchmark_task_id`, task `question_id` / `error_category`, and `BenchmarkResult.partial`. `20260819_0005` adds run-attempt and provider-call ledger tables, run cost breakdown columns, final Wayback metadata, environment-identity columns, built-in dataset identity, and the remaining foreign keys. `20260819_0006` adds `ForecastRunAttempt.provider_request_count` so attempt totals stay attempt-specific. `20260821_0007` adds versioned `forecast_contracts` while leaving existing `resolution_contracts` and forecast rows intact. `20260821_0008` adds `forecast_graphs` and `forecast_nodes` as separate planning tables without changing existing forecast records. `20260821_0009` adds `evidence_claims` with foreign keys to existing evidence items and Forecast Nodes; no existing evidence or forecast row is rewritten. `20260822_0010` adds `forecast_node_runs`, uniquely keyed by forecast run and graph node, without rewriting legacy tracks, evidence, or forecast versions. `20260822_0011` adds confidence, raw and normalized weights, dependency factor, and contribution columns with compatibility defaults for existing node-run rows. `20260822_0012` adds nullable evidence coverage and non-null coverage-count columns to existing benchmark results with compatibility defaults. `20260822_0013` adds uncertainty-note and model-identity audit fields to node runs, with compatibility defaults for existing rows. `20260823_0014` adds immutable `forecast_aggregations`, uniquely keyed by forecast run, with stored node contributions and calculation trace. `20260823_0015` adds durable `graph_execution_failures` with run, optional node, stage, code, and message fields. `20260823_0016` adds versioned real `evaluation_datasets` and resolved `evaluation_questions` without rewriting existing forecast or benchmark records. `20260823_0017` adds controlled `forecast_experiments`, `forecast_experiment_runs`, and `forecast_experiment_results`, linked to but not rewriting the frozen dataset and existing forecast records. `20260823_0018` adds internal `forecast_failures` linked to controlled runs, without changing any stored forecast probability or result. The existing execution aggregation JSON remains intact for compatibility. Isolated unit tests may still call `create_all`. Fresh empty-to-head and original-MVP-to-head databases must match on tables, columns, nullability, keys, and indexes, allowing only the documented SQLite representation differences. `PRAGMA foreign_key_check` must be empty. Back up `data/forecastlab.db` before the first launch after an upgrade (`cp data/forecastlab.db data/forecastlab.db.bak`). Do not treat the local database as a production cluster.

Migration `20260823_0019` adds an optional category to real evaluation questions for curated benchmark taxonomies. Existing rows remain `NULL`, so previously frozen question and dataset hashes are preserved. Migration `20260823_0020` adds research-plan, query, source-check, criticality, and impact audit fields to graph execution failures without rewriting existing failure or forecast records. Migration `20260824_0021` adds one immutable `research_plans` row per Forecast Run, including selected and skipped node IDs, priority scores, budget allocation, and creation time; existing runs and forecast records are unchanged. Preflight cost components are embedded in the existing `ForecastRun.execution_context_json` document and therefore add no migration.

SQLite strips timezone info on read. Health checks, watch polling, and latency math always run datetimes through `as_utc`.

## Request commit timing

FastAPI dependencies that `yield` a session commit *after* the HTTP response is sent. Write endpoints therefore call `db.commit()` before returning so a follow-up operationalize or worker claim can see the row.

## UI proxy

The Next.js app calls relative `/api/...` and `/demo/...` routes. Catch-all App Router handlers forward those requests to `FORECASTLAB_API_ORIGIN` (default `http://127.0.0.1:8765`) so the browser does not depend on cross-origin access to the API port. Docker Compose sets `FORECASTLAB_API_ORIGIN=http://api:8765` on the web service.

## Version and Python lock

Application version `0.3.1` lives in `packages/forecasting/forecastlab/version.py`. The Python package, FastAPI app, frozen environment identity, `/health`, `/api/meta`, and the Lab nav derive from that file. Real experiments require a committed `uv.lock` (or `poetry.lock`) hash. Synthetic experiments may still run when explicitly marked synthetic. Local scripts, GitHub Actions, and Docker Compose install from that lockfile instead of resolving broad minimum versions on every run.
