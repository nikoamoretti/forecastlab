# Daily Claude forecasts

A scheduled Claude Code routine adds forecasts every weekday. From 2026-11-10 the research runs on Claude Haiku (a separate headless `claude -p` run per pass, five passes per question) on the owner's Mac (full web access, his Max subscription), with the routine's `fill` as the fallback, never by the forecaster itself; Grok and Cursor were dropped at the owner's request on 2026-11-09. Before that Cursor researched on the owner's Mac and Claude Sonnet filled the gaps (2026-10-23). The only metered calls are the judge panel's, capped at $2 a day. Since 2026-10-31 the panel is one judge, Claude Sonnet 5.5, run through the routine's own Claude Code session on the owner's Claude account instead of OpenRouter credit (owner's call; [JUDGE_PANEL.md](JUDGE_PANEL.md)), and data comes from keyless official sources and Polymarket's public API.

## What one run does

1. **Merge yesterday's run.** Merge any open `claude/daily-forecasts-*` pull request whose CI is green.
2. **Prepare questions.** Run `python scripts/daily_forecasts.py prepare`. It applies the current fast selection rule, `fast_fred_question_selection_v3` (at most one jobless claims question and one week-ahead 10-year yield question, thresholds at the latest observed value, none for an indicator that still has an unreleased question) and skips targets already in any artifact. It writes `artifacts/prospective_daily_<date>/` with the statistical baseline's forecasts and `questions.json`. If there is nothing new, skip to step 4.
3. **Read the research, then forecast.** The research is not done in Claude's session and costs no Claude tokens. The Mac's LaunchAgent job (`cursor_research.py daily`, see [CURSOR_RESEARCH.md](CURSOR_RESEARCH.md)) researches every new question with Claude Haiku in five passes and pushes `research.json`. The routine's `fill` below is only the fallback for questions the Mac did not research: cloud sessions cannot open web pages, so it works from snippets and you should expect no checked quotes from it. The **download** step then fetches every cited page and checks the quotes. Before forecasting any question set:
   - Check that `research.json` is on the daily branch. Run `python scripts/cursor_research.py fill` (today's branch; `--branch` for another; it also creates and prepares the branch if needed): headless Claude Haiku runs (model, passes and timeout from `configs/research.json`) with only web search and fetch research every question still without research or listed under `failed`, pushes `research.json` and asks for **download**. Wait for that run, then pull. If there is still no research by 15:00 UTC, **skip the day**: forecast nothing, run no judges, and say so in one line. The forecaster itself never searches the web.
   - Run `python scripts/cursor_research.py digest <dir> ...` and read each question's evidence: dated facts with their source, the base rate, what is different this time, the case for the other outcome (a separate research pass that looks for the strongest evidence against the way the first two lean) and the open unknowns, then your own earlier forecasts on related questions (same topic, a shared name or word; pending or decided in the last 30 days; your probability only). Keep your answer coherent with those where they describe the same or nested outcomes; if the evidence has changed, say why in the rationale. Skip any question the digest says has no research (research failed for it), and the same for one where `research.json` lists it under `failed`. That includes a count/total question (posts, outages, "5-7 times", amount raised) whose research could not read the live number: `research()` files it under `failed` with "no running tally read for a count/total question; not forecast" instead of keeping its evidence, because forecasts made from a typical rate alone were 2-5% on questions that resolved yes. The digest prints "No research for this question: SKIP it (...)", and `record --skip-failed` lists it under `skipped` as "no live tally for a count/total question". When the tally is read, nothing changes. Do not forecast it; step 6 records it as skipped.
   - Do not search the web. Forecast from the digest alone.
   - The forecaster reads only the saved digests and writes its forecast files and briefs in a folder outside the repository; a later step records them. It never opens `market_snapshot.json`, a `forecasts.json`, `calls.json` or `scores.json` of any day, or `data/track_record.json`: they hold market prices, also of open questions on the same subject. On 2026-11-10 the forecaster printed an earlier day's `forecasts.json` to look up the record format and saw the price of a related Bitcoin question, so that day's three Bitcoin forecasts carry an integrity note and are unscored.
   - When the forecaster hands back, check what it opened: `python scripts/forecaster_audit.py <its transcript, or its subagent id> --folder <that folder>` reads the forecaster's transcript and lists every tool call that reached outside the folder (another path, `..`, the home folder, the web, `git` or `gh`, a tool other than reading and writing files). It prints what each call asked for, never what came back. Exit 0 means every call stayed inside; put "Forecaster audit: clean" in the pull request. Exit 1 lists the flagged calls: if one opened a file or page that can hold the price of an open question, treat every question in that file as seen, add an integrity note to each of the day's forecasts on the same underlying (all of them when you cannot tell), change no probability, and say so in the pull request. Exit 2 means the transcript could not be read: say that in the pull request, never call it clean. The audit catches mistakes, like the one of 2026-11-10; it is no proof against a forecaster that hides what it does.
   - A count/total question (posts, outages, amount raised, "between N and M") opens with `LIVE TALLY`: the number read from the resolution source, its time, the rate, a straight-line projection to the deadline and the daily rate each threshold needs. Start from that, not from a typical rate; a projection ignores bursts and slowdowns, so say why you move off it. A `WARNING: no running tally found` means the count was not read: be less sure. An asset-price question may carry one `Price math (thin-tailed, tends to underrate sudden dips)` line: a reference, not the call, and weigh it up for dips and crashes.

   Claude then forecasts every researched question in `questions.json`, once per question at high reasoning effort (owner's call, 2026-10-24: reasoning effort is the best-supported accuracy gain in the published AI forecasting results).
   - Start with the base rate in the digest: the reference class and counts, then the baseline probability and recent history, then what the digest says is different this time, then weigh the case for the other outcome against it.
   - Adjust only for evidence in the digest, and prefer sources whose quotes were checked.
   - Keep probabilities coherent across nested thresholds and within [0.02, 0.98].
   - Write a 2–4 sentence rationale for each forecast, with dated source URLs from the digest.
4. **Answer the owner's questions.** The owner asks questions on the app's **Ask a question** page. With `FORECASTLAB_PASSPHRASE` set to the owner passphrase, `python scripts/question_requests.py waiting` lists the waiting ones.
   - For each, write a precise resolution rule: what counts as yes, the resolution date, and the source that will decide it. Then forecast it as in step 3, with a short topic such as "Tech" or "Interest rates".
   - Save the answers as `{"forecast_made_at", "answers": [{"id", "question", "topic", "resolution_criteria", "resolution_date", "resolution_source", "probability", "rationale", "sources"}]}` and run `python scripts/question_requests.py record <file>`. The ids must be the request ids.
   - After the pull request is pushed, run `python scripts/question_requests.py answered <id> ...`.
   - For an asked question whose resolution date has passed, check the named source and run `python scripts/question_requests.py outcome <artifact_dir> <id> yes|no --note "<what happened>" --source <url>`.
5. **Forecast market questions.** Run `python scripts/market_questions.py prepare`. It applies `polymarket_selection_v7` (v6 plus the $2,500 floor below; v6 added the open-event rule below; v5 added the cluster caps;  v4 skipped markets whose rules allow settling more than 30 days after trading closes) and writes `artifacts/prospective_markets_<date>/`, with up to 18 Polymarket questions:
   - closing in 2–10 days, so results come in quickly, and not a "next prime minister/president" market, which settles only when someone takes office;
   - at least $2,500 traded (v7, 2026-11-09; $10,000 before). Thinner markets are a weaker benchmark: a price set by few traders moves on one order, so beating it is a lower bar. Each recorded question keeps the floor it was chosen under (`volume_floor`);
   - priced between 5% and 95%;
   - one per event and at most four per topic a day, and no event that already has an open (unresolved) question from an earlier day (same event page, whether recorded or only selected so far), so one event's outcome is counted once;
   - cluster cap: skipped when 5 questions in the same topic are already pending with a resolution date within 1 day of its own (counting those chosen earlier in the run), and at most 2 pending questions about the same asset (Bitcoin, Ethereum, gold, oil, the S&P 500 ..., named in the title) resolving within a day of each other.

   Since `polymarket_selection_v8` (2026-11-10) Tech events need only $1,000 traded (`TOPIC_MIN_VOLUME`); every other topic stays at $2,500. On 2026-11-10 Polymarket had 17 tech events closing in the window: one had a market passing every rule at $2,500, five at $1,000 and seven at $500. Tech is the topic with edges under test and gets about 6 results a week. Each recorded question keeps its `volume_floor`, so scores can be split by volume.

   It also adds up to 10 Manifold questions (`manifold_selection_v3`) from the economics, politics, technology and world topics, under the same window, price band, topic cap and cluster caps. Manifold trades play money, so a market needs at least 15 traders and 1,000 mana traded, and personal markets ("Will I …") are skipped. Its price is a separate benchmark, `manifold_price_v1`; from 2026-11-10 it anchors our call on a Manifold question. If Manifold can't be reached, the Polymarket questions still run.

   It also adds up to 4 Tech questions a day from Kalshi (`kalshi_selection_v1`), from its Science and Technology series. A market needs to be binary, close in 2 to 10 days, have a best bid and ask no more than 10 cents apart, a midpoint between 5% and 95%, and at least 1,000 contracts traded (`volume_unit` is `contracts`). Markets that are a threshold on a live number (`strike_type` other than custom) are left out: once-a-day research cannot judge them. One market per event, the most traded. Its price, the midpoint of bid and ask, is a separate benchmark, `kalshi_price_v1`, and it anchors our call on a Kalshi question like the others. A Kalshi question resolves when the market is finalized with a yes or no. If Kalshi can't be reached, the other sources still run.

   `python scripts/market_questions.py pool` (the "Daily run steps" `pool` step) prints the funnel for all three sources and the ids chosen from each without writing anything: markets fetched per tag, markets dropped by each rule (Manifold's window drop is split into closing too soon / too late), the cluster, asset and open-event skips, and what was chosen. On 2026-11-09 it showed Polymarket dropping 1,751 of 1,904 fetched markets on the $10,000 volume rule (8 candidates left, 4 already seen), the daily and topic limits not binding, and Manifold dropping 1,986 of 2,000 fetched on the window. The funnel also counts, for markets passing every rule except the volume floor, how many trade in each band (under $1k, $1-2.5k, $2.5-5k, $5-10k, $10k+; markets and distinct events), where the fetched markets end against the closing window (`fetched:`), and where Manifold's fetched markets close and whether the list comes back in close order (`reach:`). That run found the Polymarket fetch already inside the window and Manifold's list sorted by close time with the window reached (only about 14 Manifold markets close inside it), so the volume floor was the lever: $10,000 left 8 candidates, $5,000 left 13, $2,500 left 31 (14 chosen, with the topic limit binding).

   Forecast `questions.json` as in step 3, reading each question's `resolution_criteria` closely.
   - **Never look up the question's market odds:** not Polymarket, Kalshi, Manifold or any betting site. The market price is the benchmark we try to beat, so it must not leak into our forecast.
   - `market_snapshot.json` holds that price, and so does every recorded `forecasts.json`. The forecaster opens neither (see step 3).
   - The research tasks name no market, and answers that cite a market site or odds are cleaned before they are saved. If odds still appear in the digest, don't use them, and disclose it in that forecast's `integrity_note`. The note is shown on the question's page.
   - Save `{"forecast_made_at", "forecasts": [{"id", "probability", "rationale", "sources"}]}`. Then run `python scripts/market_questions.py record <dir> <file>`. Questions the digest has no research for (or `research.json` lists under `failed`) are left out of the file and passed with `--skip <id>[,<id>...]` or `--skip-failed`; they are printed and listed under `skipped` in `forecasts.json`, and any other uncovered question is still refused.
6. **Record the step 3 forecasts.** Run `python scripts/daily_forecasts.py record <dir> <forecasts.json>`. The file is `{"forecast_made_at", "forecasts": [{"entry_id", "probability", "rationale", "sources"}]}` (`id` is accepted for `entry_id`). It refuses forecasts made at or after an entry's cutoff, extreme probabilities, and any mismatch with the entries.
   - Questions skipped in step 3 are passed with `--skip <id>[,<id>...]`, or `--skip-failed` to skip every id under `failed` in `research.json`. They are printed as skipped and listed under `skipped` in the supplement with a reason ("no research" or "research failed or timed out"). Never record through a temporary directory or edit the manifest. A question that is neither forecast nor skipped is still refused, and the scorer and site simply show no Claude forecast for a skipped one.
7. **Judge panel.** Write `briefs.json` in each directory that got new questions today: the daily set, the market set and the asked set.
   - The format is `{"written_at", "briefs": {"<question id>": "<brief>"}}`.
   - A brief is 8–15 sentences built from the digest: the dated facts that decide the question, each with its source; the base rate and how it was worked out; and what would change the answer. Prefer the primary source over a write-up of it.
   - The judges also read excerpts of the `research.json` sources, so a brief need not restate them word for word.
   - It contains no probability, no lean and no market odds.
   - Judges never come from the research model (with `provider: claude`, the `model` in `configs/research.json`, now Haiku; with Cursor, the model family); `judge_panel.py` refuses to run if one does, and a judge skips the questions it researched itself.
   - **Since 2026-11-05 the routine runs no judge:** our call is Claude's own forecast (`claude_call_v1`, see [TRACK_RECORD.md](TRACK_RECORD.md)), which had beaten the combined call. The briefs are still written: the question page shows them. Until then, the routine ran `python scripts/judge_panel.py run --local <dir> ...` in its session, before asking for **finish**, and commit `judge_panel_log.json` with the forecasts it adds. It asks the Claude judge through the `claude` command and needs no key. `python scripts/judge_panel.py run <dir> ...` (in **finish**) asks the OpenRouter members, of which the panel currently has none.
   - Failed or rate-limited members are logged and do not stop the run. See [JUDGE_PANEL.md](JUDGE_PANEL.md).
8. **Second look (Tech only, from 2026-11-11).** Do this after the blind forecasts (steps 3 to 6) are recorded and committed, and before asking for **finish**. The second look is a separate forecast made after also seeing the market's price; it is an edge under test (`tech_second_look_v1` in [TRACK_RECORD.md](TRACK_RECORD.md)) and never changes Claude's blind forecast.
   - Run `python scripts/market_questions.py second-look export artifacts/<dir> --out <scratch>/second_look_packet.json`, with `<scratch>` outside the repository's `artifacts/` (the command refuses to write there). The packet holds market prices: it is never committed.
   - If it exports 0 questions, the step is skipped.
   - Otherwise start a separate subagent that did not forecast today. It reads only that packet and `prompts/second_look.md` (no web, no other files) and writes `{"<id>": {"probability": p, "note": "..."}}` to a scratch file.
   - Run `python scripts/market_questions.py second-look record artifacts/<dir> <file>`. It appends one `claude_second_look_v1` forecast per question (with `"saw_market_price": true`) to the directory's `forecasts.json`, refuses an id that already has one, and changes nothing else. Commit that file with the day's other artifacts.
   - The second look is excluded from the digest, the miss review, the confidence correction and every older call, so the blind forecaster never sees it.
9. **Score.** Run `python scripts/score_prospective_artifacts.py`. It rescores every artifact against first releases, records final Polymarket results for market questions, and rebuilds `data/track_record.json`, the data behind the app's Track record page. Commit that file with the artifacts.
10. **Commit.** Commit to `claude/daily-forecasts-<date>` and open a pull request. The pull request's server timestamp shows the forecasts existed before the releases. The next run merges it once CI is green.
11. **Notify.** Send the owner a short, verdict-first note only when something resolved or a run failed.

**Learning from results.** `cursor_research.py digest` starts with the forecaster's own record so far: how often it was right at each confidence level, by topic, and its latest misses with what it said. Read it before forecasting and use it to set how sure to be, never to override the evidence. Misses also feed the researcher: `python scripts/miss_review.py export` packs them up for a review and `apply` turns the lessons into per-topic research checklists ([CURSOR_RESEARCH.md](CURSOR_RESEARCH.md#learning-from-misses)). From Oct 24 our call is a weighted median: each forecaster counts by its record on the questions decided by then (Brier score shrunk toward a coin flip's by 10 results). The call is saved in the directory's `calls.json` the first time it is built and never recomputed, so later results cannot rewrite it. Claude's own probability also gets a confidence correction from 2026-10-31 (`claude_calibrated_v1`, frozen in `calibrated.json` the same way, shown on the question page and scored beside the benchmarks; our call for questions first forecast 2026-11-06 to 2026-11-09, and a tracked shadow from 2026-11-10 because it scored worse than Claude's own forecast out of sample, so it is no longer our call from 2026-11-10). From 2026-11-10 our call starts from the market price (`market_anchored_call_v1`) and is that price unless a proven edge applies (`DEFAULT_MOVE` is 0.0, the owner's decision of 2026-11-10); a call that an edge allows to move still stays at the price when the question's `research.json` shows weak research (failed, no findings, or a warning); questions with no market price keep Claude's raw forecast. How far it may move is a tested choice: `DEFAULT_MOVE` and the `CALL_RULES` registry in `track_record.py` hold the default and the rules under test, and `summary.edge_tests` scores each rule on new results until it clears the bar (40 questions, 10 resolution days, the 90% interval below zero) and is promoted by a reviewed one-line change. One of the rules under test is a model that learns from results (`learned_model_v1`: the price corrected by how prices and Claude's disagreements with them have turned out, re-fitted by the builder on every decided question and frozen per question in `learned.json`; it costs nothing to run and holds prices, so it is never read by the forecaster or printed). The price is used only by the track-record builder when it freezes the call; the forecaster still never sees it, and Claude's own forecast stays tracked as "Claude alone"; see [TRACK_RECORD.md](TRACK_RECORD.md).

**What each question page shows.** `build_track_record.py` also writes `data/research/<directory>.json`: per question, who researched it and when, the dated facts, base rate, open questions and sources (with whether their quotes were found on the page), the brief the judges read, and every judge call including failures. Downloaded page text and market odds are left out. The question page shows it as "How this forecast was made" and "The research".

**Results every day.** Scoring must not wait for a forecasting day. A separate scheduled check runs every evening (weekends included): it creates `claude/daily-forecasts-<date>-results` from the base, pushes `{"step":"finish","dirs":[]}` so Actions only re-scores, and merges the pull request if anything changed. A Polymarket market counts once it is closed and pays exactly 1 and 0, with no dispute and more than six hours past its end (UMA's challenge window is two hours). The site groups past-due questions under "Waiting for results" using today's date, not the date the record was built.

## Honesty rules

- Never use information published after the forecast time.
- Never edit a recorded forecast. A later view goes in a new day's artifact.
- Holidays without a published value resolve as cancelled, not as yes or no. So does a Polymarket market settled 50/50.
- A market closed before its event was decided does not count yet. A Manifold creator can close a market early (2026-11-12: the Alaska Senate question was closed as No while the race was uncalled and Polymarket's twin question was still open). When a result is found to be early, set it aside with `python scripts/market_questions.py hold <dir> <id> --until YYYY-MM-DD --reason "..." --source <url>`: the question is open again, `resolve` skips it until that day and then reads the market again, and the reason stays in `forecasts.json` under `resolution_hold`. Check the official result on that day before trusting the market's answer.
- Market questions are forecast without looking at any market's odds.
- Judges see only the question, its rule, Claude's brief and excerpts of the fetched sources. They never see Claude's probability or a market price.
- The scorer reports Claude, the statistical baseline and every earlier method side by side, with the number of scored questions.

## Running from a locked-down container

A cloud session may not reach FRED, Polymarket, Manifold, Kalshi or OpenRouter, may have lost the OpenRouter key when its container was recycled, and cannot dispatch workflows through the Claude GitHub App. The **Daily run steps** workflow (`.github/workflows/daily-run.yml`) runs those steps in GitHub Actions with the repository's secrets and commits each result to `claude/daily-forecasts-<date>`:

- **prepare** (steps 2 and 5) creates the branch from `grok/forecastlab-mvp` if needed and runs both `prepare` commands. It has no schedule: the routine's `fill` asks for it (the Mac research job did until 2026-11-10 and still creates the branch when it runs first).
- **download** (step 3) runs `research_download.py` on the listed directories after the Mac job pushes `research.json`: it downloads each cited page, checks the quotes against it and keeps the page text around them.
- **research** is retired (Tavily search through `research_pack.py`); it is kept only for hand runs.
- **conflict-score** runs `scripts/conflict_panel.py score --fetch` (UCDP's host is blocked in locked-down containers) and commits `artifacts/conflict_panel_v1/live_score_*.json`. It needs no secrets and logs a clear message, committing nothing, if UCDP has not published the target month yet.
- **finish** (steps 7 and 9) runs the judge panel's OpenRouter members (none since 2026-10-31; the Claude judge runs in the routine's session first, step 7) on the listed directories, scores, and starts CI on the branch, since pushes made by the workflow start no CI.

To run a step, push a commit to the daily branch that adds `daily-run-request.json`, for example `{"step": "finish", "dirs": ["artifacts/prospective_markets_<date>"]}`. The workflow removes the file when it is done. The order is prepare, research (on the Mac), download, then finish. Between steps, `git pull` the branch, read the digests, forecast, run the `record` commands (they need no network), write `briefs.json`, and push. People can also start any step, or `check-key`, from the Actions tab.
